# Git Glance 设计

> 状态：草稿，等作者确认
> 日期：2026-11-17
> 本文按"可以公开"来写：不含任何公司、项目的名字和数据。仓库建好后移到仓库的 `docs/design.md`。

## 一、要做什么、为什么

用 git 同时做好几个需求的人，常见做法是一个需求一个工作目录（`git worktree`），或者在一个目录里来回切分支。时间一长就弄不清：哪个文件夹放的是哪个分支、哪个分支落后线上、哪个已经上了测试、哪个已经上线、文件夹可以删掉了。每次都要敲一串命令去查，敲错了还可能影响别人。

现有工具各缺一块：

- 只列工作目录、不讲状态：VS Code 自带的工作目录列表、Git Worktree Manager。
- 画出所有人的全部提交：Fork、Git Graph、IDE 自带的 Git 日志。大仓库里自己的几个分支淹没在几千个别人的提交里。
- 关键功能收费：GitLens 的工作目录视图，私有仓库要付费。
- 大多带「推送」「拉取」「同步」按钮，点错会改到远程、影响别人。

本插件要做到：**一眼看清自己所有分支在哪、处于什么状态，点一下完成常用操作，并且从设计上保证不会影响别人。**

给谁用：用 git 的开发者，尤其是同时做多个需求、仓库里有多条长期并行的主干（比如几条产品线、几个大版本）的人。

## 二、目标、不做什么、底线

**目标**

1. 每个仓库一张图：每条主干单独一块，只画和自己有关的点，也就是分支从哪拉出来、自己的提交、合回主干的那一点；别人的提交压成"··· N 个提交"一行。
2. 每个分支的状态一眼可见：和线上差多少、有没有没提交的改动、比主干落后多少、上测试了没有、上线了没有、文件夹能不能删。
3. 常用操作点一下完成，用户不需要记任何命令。
4. VS Code 一家（含 Cursor、Windsurf、VSCodium 等）和 JetBrains 一家（IDEA、PyCharm、WebStorm、GoLand、Android Studio 等）都能装；其他编辑器的用户用浏览器版。Windows、macOS、Linux 都能用。
5. 做精：大仓库不卡，三个系统都测过，文档和截图完整，上架各编辑器的插件市场。

**不做（第一版）**

- 提交、推送、拉取（会产生合并提交的那种）、合并、变基、删除远程分支。
- 暂存（stash）列表、标签、多个远程仓库的管理、给分支写备注。
- Visual Studio、Eclipse、Vim/Neovim 的专门外壳（这些编辑器的用户用浏览器版）。

**底线：违反任何一条就算失败，哪怕功能都对**

- **不改动远程的任何东西**：不推送、不删远程分支、不改远程设置。对远程只做读取（`fetch`）。
- **不丢用户的东西**：不丢没提交的改动，不丢没推送的提交。只要有不安全的情况就不做，并且说清楚是哪个文件、哪个分支挡住了。
- **不把主干合进需求分支**：发版时需求分支会被合进发版分支，分支里带着的主干新提交会跟着一起上线。
- **不在用户的仓库里写任何文件**：设置、记录都放在用户自己的配置目录里。

## 三、界面

### 3.1 两个视图，同一套内容

- **侧边栏窄版**：常驻在编辑器侧边，和文件树并排。
- **大窗口**：在编辑器中间开一个标签页。侧边栏里点 ⤢ 打开。浏览器版只有大窗口。

两个视图都能在「列表」和「分支图」之间一键切换。

### 3.2 大窗口的布局

```
┌ 仓库标签：[ repo-a ] [ repo-b ] [ + ] ─────────────────────────────────────┐
│ [⟳ 全部对齐线上] [＋ 新建需求文件夹] [⇄ 对比两个分支] [≡ 操作记录]          │
│                         [列表|分支图]  [打开方式：VS Code ▾]  [☾ 深色]      │
├──────────────┬──────────────────────────────────────────────────────────┤
│ ▾ 主干 main   │ ▾ 主干 main                                  ⋮⋮ 拖动排序   │
│   ● main  ✓  │  ◉ main 最新一点                                           │
│   ● login…   │  │ ●── feature/login-page  [有改动]          (橙)         │
│   ● search…  │  │ ● Add login form                                       │
│ ▾ 主干 v2    │  ○ （从这里拉出，不写字）                                   │
│   …          │  ┊ ··· 6 个别人的提交                                      │
│ ▸ 看不出来(1) │  │ ●── feature/search  [已上测试]            (绿)         │
│ ▸ 旧分支(5)   │  ○                                                         │
│              │  ┊ ··· 227 个别人的提交                                    │
│              │  ◌╌╌ fix/typo（淡、虚线）                                   │
│              │ ▾ 主干 v2 …                                                │
│              │ ▸ 看不出来属于哪条主干（1）  拖到上面任意一块               │
│              ├──────────────────────────────────────────────────────────┤
│              │ 详情：分支全名 [复制] · 文件夹 · 属于哪条主干、从哪拉出 ·   │
│              │ 和线上 · 改动的文件 · 上测试 · 上线                         │
│              │ [在编辑器打开] [复制分支名] [和…对比] [删除文件夹（不可用：原因）]│
└──────────────┴──────────────────────────────────────────────────────────┘
```

- 时间从上往下，最新的在上面。
- 每条主干一块，可以折叠，顺序可以拖动。主干和主干之间不画连线。
- **主干也能点**（作者 11-19 定）：点主干的名字（列表的分组标题、分支图每块的标题）看主干详情：全名、比较时用哪个（没有本地分支时是 `origin/main` 这样的远程分支）、最新提交、本地分支和线上比怎样、哪个文件夹签出着它、测试分支和上线分支（没设就写没设置，提示去设置里设）、下面有几个分支；按钮只有在编辑器打开（有文件夹时）、复制名字、和…对比（先选好这条主干）。名字前的箭头只管折叠。
- **分支图只写主要的**（作者 11-18 定）：每行只有一行字。分支那一行是分支名加最要紧的一个状态（有改动 > 落后线上 > 文件夹已不存在 > 可以删除文件夹 > 上测试/上线进度 > 和线上一致）；分支自己的提交只写提交说明；拉出点只画一个空心点；已合进主干的只画淡色虚线和名字。文件夹、其他状态、提交号、日期都放进详情。
- **节点可以交互**：鼠标移到点上，点会加一圈并显示简短提示（分支全名和最要紧的状态；主干的点显示提交号）；移到某个分支上，这条分支整条线高亮、其他分支变淡。点一个点和点那一行一样：分支和它的提交显示分支详情（点提交还显示这个提交的号码、说明、日期、上没上测试和上线）；主干上的点显示这个主干提交，以及哪些分支从这里拉出。选中的点一直带着圆圈。
- 详情区显示全部状态和可用按钮。不能用的按钮变灰，并写明原因。

### 3.3 侧边栏窄版

同样分块、同样配色，竖着画"鱼骨"：主干是一根竖线，每个分支从拉出来的点斜着伸出去，刺上的点是提交，已合回去的用淡色虚线绕回主干。和大窗口一样每行只写主要的，点一个点，详情在这一行下面展开。

### 3.4 名字

- 每行显示的是**分支名**，文件夹名放在详情里（列表视图第二行小字仍写文件夹名和状态）。原因：分支名是大家共用的，文件夹名是每个人自己起的；很多人只有一个文件夹，没有文件夹的分支也要有名字。
- 可以设置一个"隐藏的前缀"（比如每个人分支名前面都带的自己名字），显示时去掉；鼠标停上去显示全名。

### 3.5 颜色

- 主干用中性灰。
- 需求分支按**分支名最后一段**取色：最后一段相同的分支同一个颜色。同一个需求在两条主干上各有一个分支时（比如 `v1/login-page`、`v2/login-page`），一眼就能对上。
- 已经合进主干的分支颜色变淡、画成虚线。
- 调色板约 12 种颜色，深色和浅色主题下都要分得清。

### 3.6 主题和语言

- 主题跟着编辑器走（深色、浅色），也可以手动切换。
- 界面语言跟着编辑器走：中文环境显示中文，其他显示英文。

## 四、概念和判断规则

### 4.1 分支的角色

| 角色 | 是什么 | 默认 | 用来做什么 |
|---|---|---|---|
| 主干 | 长期存在、需求分支从它拉出来的分支，可以有多条 | 远程的默认分支（`origin/HEAD` 指向的那条） | 分块画图；判断需求分支属于哪条 |
| 测试分支 | 每条主干可以配一条，提交先进这里测试，不合回主干 | 不配 | 判断"上测试了没有" |
| 发版分支 | 可以配多条，上线时需求分支会被合进去 | 不配 | 判断"上线了没有" |
| 需求分支 | 其余本地分支 | — | 画成从主干伸出去的分支 |

用户在侧边栏点一下就能把一个分支设成主干、测试分支或发版分支。

补充规则（审稿后补定）：

- **角色记的是分支名，比较时用远程的那份**：主干、测试分支、发版分支记的是名字（如 `main`）。判断"上测试""上线""落后主干"时，用它在远程的那份（`origin/main`），没有远程的才用本地的。本地那份自己和线上差多少，单独显示。
- **只在远程的分支也能设角色**：在侧边栏搜到后同样可以设，不要求本地有一份。
- **发版分支和测试分支一样，挂在某条主干下面**：一条主干可以挂多条发版分支，只用来判断这条主干下的需求分支。

### 4.2 一个分支属于哪条主干

1. 对每条主干算一次：这个分支里有几个提交是这条主干上没有的。
2. 数字最小的那条主干，就是它拉出来的地方。数字是 0，说明已经全部合进这条主干了。
3. 几条主干的数字一样时，就算不出来（通常是分支刚拉出来、还没有提交，正好停在几条主干都有的旧代码上）。这时按顺序用：
   - 用本插件「新建需求文件夹」建的分支：建的时候记下的起点；
   - 用户以前手动拖过的：记住的那一块；
   - 都没有：放进「看不出来」那一组，等用户拖。

### 4.3 每个状态怎么算

| 状态 | 怎么算 |
|---|---|
| 和线上 | 和它跟踪的远程分支比，多几个、少几个；没有跟踪的远程分支就显示"没推送过" |
| 改动 | 只对放在某个文件夹里的分支：有几个改了没提交、几个新文件没加进 git |
| 比主干落后 | 主干上有、这个分支没有的提交数 |
| 上测试 | 对这个分支自己的每个提交，按顺序比，任一条对上就算已在测试分支里：① 提交本身已经在测试分支里；② 改动内容相同（"挑"过去的提交号会变）；③ 内容对不上时，按提交说明（第一行）在测试分支里找相同的（挑的时候解决过冲突，内容就变了）。整个分支显示"已上测试"、"部分上测试（3/4）"或"没上测试"，详情里列出每个提交是靠哪一条对上的 |
| 上线 | 对需求分支所属主干、以及挂在这条主干下的每条发版分支，用同样的办法判断。一行里只显示一个总结：已上线（全部都进了）、部分上线（3/14）、未上线；详情里逐条列出进了哪些、没进哪些 |
| 可以删除文件夹 | 同时满足：放在一个文件夹里（不是仓库的主文件夹）、没有没提交的改动、没有没推送的提交、自己的提交都已经在所属主干里 |

补充规则（审稿后补定）：

- **"已经在某条分支里"统一按四步判断**：① 提交本身在里面；② 改动内容相同；③ 提交说明相同；④ 压缩成一个提交的合并：把整个分支从拉出点到最新的改动合起来，和那条分支上拉出点以后的单个提交比内容。"已合回主干"（淡色虚线）、"可以删除文件夹"、"上测试"、"上线"都用这套判断。4.2 判断归属的那个数字只按①算，因为它只用来比大小。
- **"没推送的提交"**：不在任何远程分支里的提交（不只看它跟踪的那一条）。插件自己建的分支不跟踪远程，远程分支合并后常被删掉，只看跟踪的那条会误判。
- **删除文件夹永远不删分支**，所以就算第③步按提交说明对错了，提交也不会丢；删除文件夹时会丢的只可能是文件夹里的文件，见第五节。

### 4.4 分支图怎么压缩

每条主干一块，从新到旧只画这些行：

- 主干的最新一点；
- 每个需求分支的提交（一个分支连续的提交超过 3 个时，只画最新的和"··· 另 N 个"）；
- 每个需求分支拉出来的点；
- 已合回去的分支合进主干的点；
- 中间别人的提交压成"··· N 个提交"一行，点开可以展开。

显示哪些分支：所有本地分支，加上放在文件夹里的分支。只在远程、本地没有的分支不画（大仓库可能有几千个），只能在侧边栏里搜到。

**旧分支**（审稿后补定）：不在任何文件夹里，并且满足以下任一条的本地分支：已经全部合回所属主干，或者最后一次提交在 30 天以前（天数可以在设置里改）。它们不画进分支图，只在侧边栏「旧分支」一组里列出，点开能看状态、能切换、能对比。

## 五、操作，以及每个操作什么时候不让做

| 操作 | 做什么 | 什么时候不让做、怎么提示 |
|---|---|---|
| 读线上最新状态 | 打开插件时和点刷新时，从远程读一次（会把远程已删除分支的本地记录一起清掉）。不定时偷偷读 | 读失败（网络、登录）就保留上次的结果，标出"读线上失败"和原因，自动重试一次，再给一个重试按钮。读的时候不允许弹出命令行要密码，要密码就算失败 |
| 全部对齐线上 | 先读一次线上，再把"只落后、不领先"的本地分支追到线上：没放在任何文件夹里的，直接追；放在文件夹里的，只有文件夹里没改动时才追。只用"只能往前追"的方式 | 有改动、有没推送的提交、和线上分叉了的，一律跳过。做完列出：追了哪些（从哪个提交到哪个提交）、跳过了哪些、为什么 |
| 打开 | 把分支所在的文件夹在编辑器里打开（新窗口）。浏览器版用设置里选的编辑器命令打开 | 分支不在任何文件夹里时，按钮换成「切换」或「新建文件夹」 |
| 切换 | 在用户选的文件夹（默认是仓库主文件夹）里切到这个分支 | 那个文件夹里有改动就不切，列出是哪些文件；这个分支已经放在别的文件夹里，就改成提示"去那个文件夹"并给出打开按钮 |
| 新建需求文件夹 | 选一条主干作为起点（用它在远程的最新位置）、填分支名、确认文件夹位置（默认放在仓库旁边），新建分支和文件夹，然后打开。记下起点 | 分支名已存在、文件夹已存在就不建。不设置跟踪的远程分支，不推送 |
| 删除文件夹 | 把这个需求的文件夹从硬盘上删掉，分支和提交都保留（作者 11-17 定名：原叫"收起"，容易被当成界面折叠；界面上所有文字都写"删除文件夹"，确认弹窗写明"会从硬盘上删掉 xxx 文件夹，分支保留"） | 不满足 4.3 的"可以删除文件夹"就不让点，写明原因。不使用任何强制删除。仓库的主文件夹永远不能删除。动手前先试着把整个文件夹改个名：改名失败说明还有程序（比如编辑器窗口）开着它，就提示先关掉，什么都不删，避免删到一半停住。被 git 忽略的文件（作者 11-17 定）：常见的编译产物和依赖目录（如 `target`、`build`、`dist`、`node_modules`，完整清单交给做的人定，写进说明）直接删；其余被忽略的文件（`.env`、IDE 设置、个人笔记等）先按原来的相对路径复制到插件自己的备份目录（配置目录下，按仓库、文件夹名和时间分开），复制成功才删。备份失败就整个不删。删除后告诉用户备份在哪、有多大；备份不自动清理，用户在设置里手动清 |
| 对比两个分支 | 列出两边各自独有的提交、不同的文件；点文件看具体改了什么（VS Code、JetBrains 用编辑器自带的对比窗口，浏览器版在页面里显示） | 只看不改 |
| 复制分支名 | 把全名放进剪贴板 | — |
| 操作记录 | 插件做过的每一个会改动本地的操作都记一行：时间、仓库、操作、分支、执行的 git 命令、改动前后的提交号、结果 | 只记录，不提供撤销；改动前后的提交号足够让人手动恢复 |

**命令白名单**：核心程序里列出允许执行的 git 命令，白名单以外的命令在代码里就执行不了，并且要有测试证明这一点。至少不允许出现：`push`、`reset --hard`、`branch -D`、`clean`、`rebase`、`stash drop`、带强制选项的 `worktree remove`、以及任何会产生合并提交的 `merge`、`pull`。

## 六、怎么搭

### 6.1 选过的做法

| 做法 | 说明 | 结论 |
|---|---|---|
| 一个核心 + 每个编辑器一层外壳 | 判断规则和操作写在一个核心程序里，界面写一次，VS Code、JetBrains 各套一层薄外壳，浏览器版直接用核心 | **选这个**：判断规则和界面都只写一次，编辑器越多越划算，浏览器版几乎白送 |
| 先只做 VS Code 扩展 | 全部写在 VS Code 扩展里 | 不选：判断规则和 VS Code 绑死，做 JetBrains 版要重写 |
| 独立桌面软件 | 像 Fork 那样单独的软件 | 不选：作者要的是装在编辑器里的插件 |

### 6.2 各部分

- **核心**：用 Go 写，每个系统和架构编译成一个单独的可执行文件（Windows、macOS、Linux 各 x64、arm64），用户不用另装运行环境。核心调用用户电脑上已有的 git，通过标准输入输出和外壳交换 JSON。还有一个"网页模式"：只监听本机地址、随机端口，地址里带随机口令，没有口令的请求一律拒绝，供浏览器版使用。
- **界面**：一份网页界面（TypeScript），VS Code 放进它的网页面板，JetBrains 放进内置浏览器，浏览器版直接打开。分支图用 SVG 画。
- **VS Code 外壳**：TypeScript。提供侧边栏视图和大窗口标签页，按系统分别打包。上架 VS Code 插件市场和 Open VSX（Cursor、Windsurf、VSCodium 用这个）。
- **JetBrains 外壳**：Kotlin，用 IntelliJ 平台的 Gradle 插件构建。提供工具窗口（侧边栏）和编辑器标签页，打包时带上所有系统的核心程序。上架 JetBrains 插件市场。**只依赖平台通用模块，不依赖 Java 插件**，这样 PyCharm（社区版和专业版）、WebStorm、GoLand 等都能装；IDE 的内置浏览器不可用时（个别远程开发环境会关掉它），提示改用浏览器版。
- **浏览器版**：核心程序的网页模式，发在 GitHub Releases。
- **设置和数据**：每个仓库的设置（主干、测试分支、发版分支、隐藏的前缀、手动拖过的归属、记下的起点）和操作记录，都放在用户的配置目录里，按仓库路径区分，不写进仓库。

### 6.3 作者电脑上要装的开发工具

Go，以及 JDK 17 或更新的版本（放在单独的文件夹里，不替换已有的 JDK）。Node 已有。

## 七、做精的标准

- **速度**：用脚本造一个大仓库来测，大约 1000 个本地分支、20 个文件夹、30 万个提交、3 条主干。在普通笔记本上：打开时先显示上次的结果，1 秒内出画面；不读线上的完整刷新在 5 秒内；刷新在后台进行，界面不卡。
- **测试**：
  - 核心的每条判断规则都用脚本临时造的仓库来测。要覆盖：多条主干、算不出来的情况、挑提交时解决过冲突（只能靠提交说明对上）、压缩成一个提交的合并、文件夹干净 / 有改动 / 有没推送的提交、游离状态（没在任何分支上）、分支已在别的文件夹里、读线上失败和要求登录、Windows 换行、路径里有空格和中文。
  - **任何测试都不碰真实仓库和用户真实的配置目录**，只用临时目录。
  - 白名单测试：证明核心执行不了白名单以外的命令。
  - 三个外壳各有冒烟测试：能装上、能显示、按钮能调用到核心。
- **自动测试**：GitHub Actions 在 Windows、macOS、Linux 上，用支持的最低 git 版本和最新版本各跑一遍，并打出所有安装包。
- **文档**：README 中英两份，截图只用演示仓库截。内容包括每个编辑器怎么装、每个状态是什么意思、"为什么没有推送按钮"，以及没签名的核心程序在 macOS、Windows 上怎么放行。

## 八、开源和信息安全

- 发在作者个人的 GitHub，MIT 协议，提交署名用 GitHub 提供的匿名邮箱。
- 先建私有仓库，自动测试通过、作者看过以后再公开；公开以后再上架插件市场。
- 每次推送前，用作者自己保存在仓库外面的敏感词表扫一遍所有要推送的文件。截图只用演示仓库。
  - 词表沿用作者已有的那份私有词表，路径只记在本机、不进仓库。格式是一行一个词：默认不分大小写，`=` 开头的区分大小写，`re:` 开头的是正则。
  - 扫描放在本机的推送前检查里：找不到词表就拒绝推送。GitHub Actions 读不到词表，不在那里扫。
  - 作者的 GitHub 账号和匿名邮箱沿用作者另一个开源仓库已经配好的那一套。
- 设计过程中用作者工作仓库画的界面草图只留在本机，不进仓库。

## 十三、以后再考虑（第一期不做）

- **简单的提交和推送**（作者 11-17 提出，第一期做完后单独设计）。初步设想的护栏，到时再和作者定：
  - 提交：只提交当前这个文件夹里、用户勾选的文件，提交前列出文件和提交说明让用户确认。
  - 推送：只推当前需求分支到线上同名分支；永不强推；主干、测试分支、发版分支一律不让推；线上比本地新（需要先合并）时不推，只提示原因。
  - 推送前列出要推上去的提交，确认后才推；第一次推送时顺带设置跟踪。
  - 这会改变"对远程只读"这条底线的说法，需要作者确认新的底线怎么写。
- **删除文件夹前先预览清单**：确认框里逐个列出会先备份的被忽略文件、会直接删掉的编译产物目录。第一期确认框只讲规则，删完列出实际做了什么。
